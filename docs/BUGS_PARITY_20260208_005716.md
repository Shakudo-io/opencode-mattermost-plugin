## Bug 1: Thinking/Reasoning Content Silently Dropped

**Severity:** Medium
**Status:** Open — Code is correct, issue is observational. Needs debug logging to confirm.
**Affected file(s):**
- `.opencode/plugin/mattermost-control/event-handlers/message.ts:94-106` (event capture)
- `.opencode/plugin/mattermost-control/formatters.ts:298-300` (rendering)

### Symptoms
- The TUI displays reasoning/thinking content (e.g., "Thinking: Listing Renamed Agents") with faded/italicized text
- Mattermost shows **no thinking content at all** — the `:brain: Thinking:` section never appears

### Confirmed Root Cause

**The code pipeline is fully wired and correct.** End-to-end trace confirms:

1. **SSE wire format** (`/tmp/opencode/packages/opencode/src/session/message-v2.ts`): Part type is `"reasoning"` (defined via `z.literal("reasoning")` in `ReasoningPart`). This is NOT `"n"` — `"n"` is used only internally in the model provider layer for the "reasoning effort" parameter, never as a part type on the wire.

2. **Event emission** (`/tmp/opencode/packages/opencode/src/session/processor.ts:62-84`): When the LLM streams `reasoning-delta` events, the processor creates a part with `type: "reasoning"` and calls `Session.updatePart()`, which publishes `MessageV2.Event.PartUpdated` to the bus with `{ part, delta }`.

3. **SSE passthrough** (`/tmp/opencode/packages/opencode/src/server/server.ts:496-510`): `Bus.subscribeAll()` subscribes to `"*"` events. The payload is serialized as-is via `JSON.stringify(event)` — **zero transformation**.

4. **Plugin handler** (`message.ts:94`): Checks `part?.type === "reasoning" && delta` — matches the wire format exactly.

5. **Plugin renderer** (`formatters.ts:298-300`): Renders `ctx.thinkingBuffer` as `:brain: **Thinking:**` block quote.

**Since the code is correct, the issue is one of these:**

- **Model doesn't produce reasoning.** Only models with extended thinking (Claude with thinking enabled, o1/o3-style models) emit `reasoning` parts. Standard Claude Sonnet/Opus without explicit thinking config does NOT produce reasoning parts — it just produces text. The TUI screenshot showing "Thinking:" may have been from a session using a thinking-enabled model that isn't the default for Mattermost sessions.
- **`delta` is empty string.** The condition `part?.type === "reasoning" && delta` is falsy when `delta === ""`. If OpenCode emits a reasoning part update with an empty delta (e.g., start/end markers), it would be silently skipped.
- **No active `ResponseContext`.** If the context was already cleaned up (e.g., race with `session.idle`), the handler returns at line 76 before reaching the reasoning check.

### Exact Fix

**Add debug logging to confirm whether reasoning events are reaching the handler at all:**

In `message.ts`, add at the top of `handleMessagePartUpdated` (after line 76):
```typescript
// Log ALL part types for debugging reasoning visibility
if (part?.type) {
  log.debug(`[PartDebug] session=${sessionId?.substring(0,8)} part.type=${part.type} delta=${delta?.length ?? 'null'} thinkingBuffer=${ctx.thinkingBuffer.length}`);
}
```

**Additionally, relax the delta check to handle empty-string edge case:**

Change line 94 from:
```typescript
} else if (part?.type === "reasoning" && delta) {
```
To:
```typescript
} else if (part?.type === "reasoning" && delta != null) {
```

Then only append non-empty deltas:
```typescript
if (delta) ctx.thinkingBuffer += delta;
```

This ensures the handler at least enters the reasoning branch and increments the counter, even if delta is empty — making it visible in the `session.idle` summary log at `session.ts:47` which already reports `reasoningParts=X`.

**No other changes needed.** The rendering code is already correct. Once reasoning events actually flow (from a thinking-enabled model), the output will appear.

## Bug 2: Stale "Processing" Post After Compaction

**Severity:** Medium
**Status:** Open — Root cause confirmed
**Affected file(s):**
- `.opencode/plugin/mattermost-control/event-handlers/compaction.ts:37-41`
- `.opencode/plugin/mattermost-control/formatters.ts:75-130` (`formatToolStatus`)
- `src/response-streamer.ts:210-256` (`recreateStreamAtBottom`)

### Symptoms
- After compaction, the old post is frozen with stale dynamic content like `💻 Processing (2m 15s)`, `🔧 bash (45s)...`, `⏳ Continuing...`
- These dynamic values never update again since the post is no longer the active stream target

### Confirmed Root Cause

In `compaction.ts:38`, the old post content is generated by `formatFullResponse(ctx)`. This function renders **live/dynamic** status elements:

- `formatToolStatus()` (line 83-130 of `formatters.ts`) generates:
  - `💻 Processing (Xs)` — based on `Date.now() - responseStartTime` (line 93-94)
  - `🔧 tool_name (Xs)...` — based on `Date.now() - activeTool.startTime` (line 125-126)
  - `⏳ Continuing...` — if `awaitingContinuation` is true (line 116-118)

These time-relative strings are computed at snapshot time and then frozen into the old post via `recreateStreamAtBottom` → `mmClient.updatePost(ctx.postId, finalizeOldContent)` (line 214-215 of `response-streamer.ts`).

**Additionally:** The compaction handler does NOT reset the response context buffers (`responseBuffer`, `thinkingBuffer`, `toolCalls`, `completedBashOutputs`, `editDiffs`, `todos`). This means the new post after compaction starts with ALL the old accumulated content, causing it to flash old content before new streaming content overwrites it.

### Exact Fix

**Step 1: Add a `finalize` parameter to `formatToolStatus`** in `formatters.ts`:

```typescript
export function formatToolStatus(
  toolCalls: string[],
  activeTool: ActiveTool | null,
  compactionCount: number = 0,
  cost?: CostInfo,
  responseStartTime?: number,
  awaitingContinuation?: boolean,
  agentName?: string,
  finalize?: boolean  // NEW
): string {
```

When `finalize === true`:
- Replace `💻 Processing (Xs)` with `✅ Completed` or just the agent name without a timer
- Replace `🔧 tool_name (Xs)...` with nothing (active tool should be treated as completed)
- Remove `⏳ Continuing...`
- Compute final elapsed time as a static value: `(2m 15s total)`

**Step 2: Add a `finalize` parameter to `formatFullResponse`** in `formatters.ts`:

```typescript
export function formatFullResponse(ctx: ResponseContext, debugLog?: ..., finalize?: boolean): string {
```

Pass `finalize` through to `formatToolStatus`. When finalizing, also strip the `" ..."` streaming suffix (this is handled by the streamer layer, but good to be explicit).

**Step 3: Use finalized format in compaction handler** in `compaction.ts:38`:

```typescript
const oldContent = formatFullResponse(ctx, undefined, true); // finalize=true
```

**Step 4: Reset response context buffers after compaction** in `compaction.ts` after line 40:

```typescript
// Reset buffers for the new post-compaction stream
ctx.responseBuffer = "";
ctx.thinkingBuffer = "";
ctx.shellOutput = "";
ctx.bashCommand = undefined;
ctx.lastBashOutput = undefined;
ctx.lastBashCommand = undefined;
ctx.completedBashOutputs = [];
ctx.editDiffs = [];
ctx.activeTool = null;
// Keep: toolCalls (cumulative), todos (persistent), cost (cumulative), agentName
```

## Bug 3: `(message deleted)` Artifacts Visible After Compaction

**Severity:** Low-Medium
**Status:** Open — Root cause confirmed (Mattermost platform behavior)
**Affected file(s):**
- `src/response-streamer.ts:220-226` (`recreateStreamAtBottom`)
- `src/clients/mattermost-client.ts:147-150` (`deletePost`)

### Symptoms
- After compaction, `(message deleted)` placeholder stubs appear in the thread where continuation posts existed

### Confirmed Root Cause

Mattermost `DELETE /api/v4/posts/{postId}` performs a **soft delete** — it sets `delete_at` timestamp but the post remains visible as `(message deleted)` in the UI. This is documented Mattermost behavior.

In `recreateStreamAtBottom` (line 220-226), continuation posts are deleted via `this.mmClient.deletePost(contPostId)` with no fallback. Compare this to `updateWithSplittingInternal` (lines 274-287) which has a fallback: when delete fails, it updates the post to `"*(message consolidated above)*"`.

The `recreateStreamAtBottom` method is inconsistent — it deletes without fallback, while the splitting cleanup has a graceful fallback.

### Exact Fix

**Replace `deletePost` with `updatePost` for continuation posts in `recreateStreamAtBottom`** (`response-streamer.ts:220-226`):

```typescript
for (const contPostId of ctx.continuationPostIds) {
  try {
    // Update to minimal content instead of deleting to avoid (message deleted) stubs
    await this.mmClient.updatePost(contPostId, "⬆️ *(see above)*");
  } catch (e) {
    log.debug(`[ResponseStreamer] Could not update continuation post ${contPostId}, attempting delete`);
    try {
      await this.mmClient.deletePost(contPostId);
    } catch (e2) {
      log.debug(`[ResponseStreamer] Could not delete continuation post ${contPostId}`);
    }
  }
}
```

This updates continuation posts to a minimal redirect message instead of deleting them, avoiding the `(message deleted)` stubs entirely. Delete is kept as a fallback if update fails.

## Bug 4: Orphaned `(continued 2/2)` Fragments After Compaction

**Severity:** Low
**Status:** Open — This is a consequence of Bug #3
**Affected file(s):**
- `src/response-streamer.ts:220-226` (`recreateStreamAtBottom`)

### Symptoms
- `(continued 2/2)` post fragments left orphaned after compaction when their parent was cleaned up

### Confirmed Root Cause

This is a direct consequence of Bug #3. When continuation posts are soft-deleted, Mattermost shows `(message deleted)` but the content (which included `*(continued 2/2)*` header) was visible before deletion. If the delete API call fails silently (catch at line 222-225 only logs debug), the continuation post remains with its full `(continued 2/2)` content.

The `recreateStreamAtBottom` method correctly resets `continuationPostIds: []` (line 245) in the new context, so new streaming won't reuse old posts. But old posts that failed to delete persist.

### Exact Fix

**Same fix as Bug #3** — updating continuation posts to `"⬆️ *(see above)*"` instead of deleting them eliminates both the `(message deleted)` stubs AND the orphaned continuation fragments. The redirect message is self-explanatory regardless of context.

## Bug 5: Multiple Compaction Notification Posts

**Severity:** Low
**Status:** Open — Root cause confirmed
**Affected file(s):**
- `.opencode/plugin/mattermost-control/event-handlers/compaction.ts:42-53`

### Symptoms
- Multiple `📦 **Context Compacted** (x1)`, `📦 **Context Compacted** (x2)` posts appear in the thread
- Each compaction event creates a new notification post instead of updating the existing one

### Confirmed Root Cause

In `compaction.ts:47-52`:
```typescript
const post = await mmClient.createPost(targetChannelId, compactionMsg, ctx.threadRootPostId);
ctx.compactionPostId = post.id;
```

`createPost` is always used. `ctx.compactionPostId` is stored but **never checked** before creating a new post. On the Nth compaction, the previous `compactionPostId` is overwritten and the old notification post is abandoned.

### Exact Fix

**Check for existing compaction post and update it** in `compaction.ts`, replace lines 42-53 with:

```typescript
const compactionMsg = `📦 **Context Compacted** (×${ctx.compactionCount})\n\n` +
  `_Context was automatically compressed to continue the conversation._`;

const targetChannelId = ctx.streamCtx?.channelId || ctx.mmSession.dmChannelId;

if (ctx.compactionPostId) {
  // Update existing notification post instead of creating a new one
  try {
    await mmClient.updatePost(ctx.compactionPostId, compactionMsg);
    log.debug(`[Compaction] Updated existing compaction post ${ctx.compactionPostId}`);
  } catch (e) {
    log.warn(`[Compaction] Failed to update compaction post ${ctx.compactionPostId}, creating new`);
    const post = await mmClient.createPost(targetChannelId, compactionMsg, ctx.threadRootPostId);
    ctx.compactionPostId = post.id;
  }
} else {
  const post = await mmClient.createPost(targetChannelId, compactionMsg, ctx.threadRootPostId);
  ctx.compactionPostId = post.id;
  log.debug(`[Compaction] Created compaction post ${post.id}`);
}
```

## Bug 6: Response Context Not Reset After Compaction (NEW — found during analysis)

**Severity:** Medium
**Status:** Open — Root cause confirmed
**Affected file(s):**
- `.opencode/plugin/mattermost-control/event-handlers/compaction.ts`

### Symptoms
- After compaction, the new streaming post briefly flashes with ALL pre-compaction content (old bash outputs, old response text, old edit diffs)
- The new post contains accumulated tool history from before compaction

### Confirmed Root Cause

The compaction handler (`compaction.ts:32-40`) updates flags and recreates the stream, but **does NOT reset any content buffers** on the `ResponseContext`:

```typescript
ctx.compactionCount += 1;
ctx.awaitingContinuation = true;
ctx.inCompactionSummary = false;
// ... recreate stream ...
// NO BUFFER RESETS
```

The `ResponseContext` retains: `responseBuffer`, `thinkingBuffer`, `shellOutput`, `bashCommand`, `lastBashOutput`, `lastBashCommand`, `completedBashOutputs`, `editDiffs`. The new post at the bottom inherits `ctx.buffer` from the old `StreamContext` (via `recreateStreamAtBottom` line 233: `ctx.buffer || "..."`), which is the full old formatted response.

### Exact Fix

**Add buffer resets in `compaction.ts` after `ctx.streamCtx = newStreamCtx`** (after line 40):

```typescript
// Reset content buffers for the new post-compaction stream
// This prevents old content from flashing in the new post
ctx.responseBuffer = "";
ctx.thinkingBuffer = "";
ctx.shellOutput = "";
ctx.bashCommand = undefined;
ctx.lastBashOutput = undefined;
ctx.lastBashCommand = undefined;
ctx.completedBashOutputs = [];
ctx.editDiffs = [];
ctx.activeTool = null;
// Preserve: toolCalls (cumulative history), todos (persistent state),
//           cost (cumulative tracking), agentName (still active),
//           compactionCount (already incremented above)
```
